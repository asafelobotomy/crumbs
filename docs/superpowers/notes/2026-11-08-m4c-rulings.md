# M4c rulings (MCP server)

These are the decisions made while building M4c where the plan or spec was silent, wrong, or overruled. Each gives the reason, and what it costs if it turns out wrong.

## Shared code with the CLI

- **Builders and printers.** CLI commands were split into pure builders (`cmd/build.rs`) and printers. On fixtures and on the dev machine, the CLI's output stayed byte-identical to `main`.
- **`execute_confirmed`.** This is the shared post-confirmation run path. It takes `AllowedRunning { None, Only(ids), Any }`, not a `force` flag.
  - Why: under a bare `force` flag, a second app that started after the user confirmed the first would have slipped through.
  - Cost: the CLI now refuses (exit 1) when an app starts while "Proceed?" is open.
- **Privilege.** `Privilege` is `pub(crate)`, and `for_run` and `for_server` share one gate. `build(env, needed, interaction, test_runner, allow_real)` takes the environment values as parameters, so tests never change the process environment.

## Escalation without a terminal

- **No terminal.** Under `Interaction::NoTerminal`:
  - the root process gets stdin from `/dev/null`;
  - its stderr is captured, capped to the last 64 KiB;
  - sudo is excluded, as is anything else that `requires_tty`.

  run0 and pkexec then need a graphical polkit agent. Without one, the run is exit 5, and `escalation_output` says why.
- **Debug hook.** The debug-only `before_execute_hook` sends its stdout to stderr, because inheriting stdout would corrupt the protocol stream.

## Plans and previews

- **Plan ids.** Ids are 16 bytes from `/dev/urandom`, with no weaker fallback.
- **Plan lifetime.** A plan is single-use and expires 10 minutes after the preview. At most 64 plans can be pending.
- **What `select` accepts.** Only paths and categories that crumbs itself found.
- **Restore by entry id.** A restore plan stores the exact history entry ids its preview showed. Apply never re-resolves the selectors.
  - Why: new history entries since the preview could have changed what a path selector matched.
  - Note: restore previews list destinations only. Core does not record the trash source.

## Confirmation (`apply`)

- **What counts as a yes.** Only two things:
  - the server's own `elicitation/create`, answered with accept and `confirm: true`;
  - an MRTR answer stored under the server-issued 128-bit key, with `requestState` equal to the plan id, after the server actually asked (`asked`).

  `finish` matches exhaustively, so only `Answer::Confirmed` runs.
- **Which client gets which path.** A client that sends `initialize`, even one asking for 2026-07-28, is negotiated down to 2025-11-25 and gets `elicitation/create`. The 2026-07-28 inline lifecycle (`server/discover` plus per-request `_meta`) gets `InputRequiredResult`. Every mismatch fails closed.
- **Clients that cannot confirm.** A client without form elicitation is refused before its plan is taken. The refusal carries the equivalent CLI command. If rmcp reports that capability missing while asking, the plan is put back under the lock.
- **Single use.** Plans are taken under the apply mutex, so two racing `apply` calls run a plan once. One `apply` waiting for an answer holds other `apply` calls until it is answered.
- **Late answers.** A yes that arrives after `expires_at` on the elicitation path runs nothing.
- **What `applied` means.** At least one action succeeded. `report` is present only when something ran.
  - A system-only plan whose admin prompt is denied gives `applied: false` and exit 5, with `manual_commands`, a mount-check `note` and `escalation_output`.
  - An exit-3 run where every action failed also gives `applied: false`.

## Server

- **stdout.** It carries only protocol frames. Warnings go out as MCP log notifications. rmcp 3.9.0 marks these deprecated (SEP-2577) but offers no replacement.
- **Text.** All returned text is sanitised for control bytes. Structured content is left as serde writes it, which escapes it.
- **Startup.** The server tightens history file modes when it starts, as every CLI command does.
- **Closing stdin.** After stdin closes, rmcp waits only 5 s for in-flight responses, so clients should keep stdin open.
